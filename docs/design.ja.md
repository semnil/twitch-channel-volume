# 設計上の主な決定

> For the English version, see [design.md](design.md).

拡張機能がなぜ今の形で作られているかを、決定ごとに 1 項目で書く。項目は、先頭の太字の言葉で呼ぶ。`docs/decisions/` の日本語の記録はその名前で引き、`AGENTS.md` は英語版 ([design.md](design.md)) の名前で引く。各スクリプトがすることは [architecture.ja.md](architecture.ja.md) にある。閉じた決定と、その理由、覆す条件は `docs/decisions/` にある。

- **自前の LUFS 計測**: Twitch にはラウドネスの API が無いので、BS.1770-4 の K 特性 + ゲート付きの Integrated LUFS を Web Audio API で測る。自分から測りに行く方式で、loudnessDb を受け取って読むだけの yt-channel-volume と対になる
- **AudioWorklet (ScriptProcessor ではなく)**: ScriptProcessor は非推奨。100ms 単位の L²+R² の積み上げは worklet のスレッドで行い、窓はメインスレッドで作る
- **計測は共有のもの**: 下に書く K 特性、worklet、メーターは、channel-volume-core の `core/loudness.js` と `audio-worklet.js` ([docs/shared-files.ja.md](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#measure))。テストと変異テストの走査もそちらで行う。Twitch に固有なのは、bridge がメーターに伝えるもの (割り戻す音量、CM のゲート、境界、CM の始まりの巻き戻し、種)
- **K 特性フィルターの係数**: BS.1770-4 の 48kHz の係数をもとにする。AudioContext.sampleRate が 48k でないときは、双一次変換の逆変換をしてから、あらためて双一次変換をして、フィルターを設計し直す (redesignBiquad)
- **索引を使った Integrated LUFS の更新**: 今のチャンネルと種別について保存した LUFS を、その値が立っている窓の数だけの最初のサンプルとして戻す (下限と上限は「セッションをまたぐ計測」にある)。直近 1 時間のブロックをリングバッファに持ち、絶対ゲートを通った値を、部分木の合計と個数を持つ平衡木に入れる。-10 LU の相対ゲートは、絶対ゲートを通った後の平均からそのたびに求め、しきい値以上の合計と個数を O(log n) で得る。そのため、入力の順番がどうであっても 2 段のゲートが成り立つ。CM 区間は Integrated の統計に入れない (CM が本編を代表する値を汚さないようにするため)
- **セッションをまたぐ計測**: 保存する LUFS は、その値が立っている窓の数 (`lastLufsWindows`) と一緒に保存し、次の計測はその数の窓を種にして始める。種を 1 窓だけにすると、1 秒に 10 窓届く新しい音が 1 秒以内にそれを洗い流し、Auto は本編の 0.4 秒分しか表していない Integrated の値からゲインを決めることになる。下限は 300 窓 (30 秒)、上限は 1800 窓 (3 分)。上限をリングバッファと同じ 1 時間にすると、種は 1 つの値に集まった重りなので、相対ゲートがその値に張り付き、配信者が本当に音を下げた後も Integrated の値が 20 分以上動かなくなる。3 分なら、同じ長さだけ見れば種の重みに届く。窓の数を持たない保存値 (拡張機能の更新より前のもの) と、読めない窓の数は、下限の重みにする。知らせる窓の数は、相対ゲートを通った窓だけを数え、種の分は、種が持ってきた窓の数に置き換える。下限まで水増しした分は測ったものとして知らせず、ゲートが落とした窓とリングバッファが追い出した窓は数えない。どの窓が種のものかは、レベルではなく、ゲーティング窓の通し番号で決める (索引はレベルをキーにしているので、種と同じレベルの音は種のノードに入る)。下限と上限の決定は、共有のメーターと一緒に channel-volume-core の [docs/decisions/measurement.ja.md](https://github.com/semnil/channel-volume-core/blob/main/docs/decisions/measurement.ja.md) に記録してある。popup が種の値をどう出すかの決定は、このリポジトリの `docs/decisions/measurement.ja.md` にある
- **Auto のゲインは Integrated の値が求めるゲイン**: ブロックごとの適用 (`applyAutoGain`) は、`AUTO_FOLLOW_INTERVAL_MS` (1 秒) に多くても 1 回、`calcGain(integrated)` をかける。`reapplyForCurrentChannel` は、チャンネルへの書き込みのたびに始まり (このタブ自身の計測の保存も含む)、`resolvePreferredGain` が返すゲインをかける。Auto がオンで Integrated の値が有限の数なら、それは同じゲインになる。今かかっているゲインより大きいゲインは、小さいゲインと同じように、すぐにかける。保存した計測値が種なので、前に見たことのあるチャンネルでは、最初のゲインは保存した計測値が求めるゲインになる
  - **保存するもの**: Auto のために保存するもの (5 秒ごとの保存での `saveMeasurement`、設定が変わった後の `saveAutoGain`) も、同じ `calcGain(integrated)`。どちらも、プレイヤーが再生中のタブからだけ送る。再生中かどうかは、最後の `lufs` の通知の `playing` で決まる。一時停止でもミュートでもないことを指し、音量やゲインが 0 のときは再生中に数える。そのため、同じチャンネルを開いた一時停止中やミュート中のタブは、どちらも上書きしない。popup の Current は今かかっているゲイン、Suggested は Integrated の値が求めるゲインなので、Auto が測ったゲインをかけている間、2 つは同じになる
  - Live も VOD も同じ。どちらも同じやり方で測る
- **HTMLMediaElement.volume ではなく GainNode**: volume は 1.0 で頭打ちになる。GainNode なら 0.0–6.0 (0–600%) を出せる
- **MAIN world / ISOLATED world の分担**: Twitch の CSP はインラインのスクリプトを禁じているので、AudioContext と fetch のフックは page-bridge.js (MAIN world、document_start) で動かす
- **だれも処理しないページの fetch**: Chrome は、ページの要求から出た「処理されなかった reject」を、その要求が通った `window.fetch` のラッパーのものとして知らせ、拡張機能のエラーの一覧に `Uncaught (in promise) TypeError: Failed to fetch` を記録する。`currentContentIdentity()` が Live・VOD・クリップのページを指している間に出た要求は、`requestMadeOnContentPage` を通して出す。Chrome が出せなかった要求の TypeError は、その呼び出しのスタックを持つ。bridge の `unhandledrejection` のリスナーが既定の動作を止めるのは、`Failed to fetch` と読める `TypeError` で、スタックに `at requestMadeOnContentPage (chrome-extension://` のフレームがあるものだけ。これは、ページに渡した promise にも、そこからつないだ promise や await した promise にも届く。リスナーは、どちらにも何も付けない。ページ自身の promise が同じエラーで reject されたとき、別のページで出した要求 (どのページで失敗しても同じ)、ほかの理由で失敗した要求 (中断も含む) は、これまでどおり「処理されなかった reject」になる。`Error.stackTraceLimit` を 0 にしているページでの失敗も同じ。そのページのスタックにはフレームが無い。`gql.twitch.tv` への要求には、bridge 自身の処理が付いていて、応答を読む。`currentContentIdentity()` は、`TWITCH_RESERVED_PATHS` が挙げる 1 区切りだけのパスを除く。その集合の写しを `page-bridge.js` に持っている (utils.js は MAIN world に読み込まれないため)。`node test.js` は、utils.js の集合の各パスで要求を出す
- **チャンネル ID の決め方**:
  - Live は、持ち主の応答が届く前だけ URL の login (`login:<name>`) を使い、GraphQL の `user.id` が分かったら、VOD と同じ数字の ID へまとめる
  - VOD は、GraphQL の応答の `owner.id` (数字で、変わらない) を使う。分からないときは `vod-owner:<videoId>`
  - クリップは、どの種類の ID も持たない。クリップには何も保存しないので、キーが要らない
  - 種別ごとの仮 ID は、数字の ID が使えない間だけ使い、その後は消えない別名で正規の ID に読み替える
- **仮 ID → 確定した ID への移行**: page-bridge は、持ち主のイベントに、GraphQL の応答が挙げたコンテンツ (ユーザーの login、または動画の id) を付ける。応答が動画を挙げていない動画の持ち主は送らない。content.js は、今の URL と合う応答だけを受け取る。そして、最初の設定の読み込みがまだ走っている間でも、currentChannel を切り替える前に、Service Worker の中で `login:<name>` / `vod-owner:<videoId>` を数字の ID へまとめる。ゲイン / Auto / LUFS の各項目は、単一の書き手が付けた更新の順番でぶつかりを解くので、別のタブからの最新の保存が残る。仮 ID から正規の ID への対応は storage に保存し、content の読み取りでも Worker の書き込みでも同じように引く
- **Saved Channels のチャンネルの不変条件**: 数字の持ち主 ID と login が対応するところでは、1 つの行にまとめる。保存して表示するリンクは、いつも `https://www.twitch.tv/<login>`。すでにある重複した Live/VOD の行は、拡張機能の更新のときに、そろえるための変更で移す
- **channelVolumes の単一の書き手**: まとめのキーを「読む・変える・書く」の一連は、background.js → channel-store.js の列だけが行う。content script と options は変更のメッセージを送る。こうして、複数のタブからの LUFS のキャッシュの保存や、Auto/手動の設定の保存が、古い全体のオブジェクトで互いを上書きしないようにする。失敗の理由は 3 つに分かれる。**store 自身が投げた例外は `reason` を名乗る**。呼び出し側の入力で、反映できないものは `invalid-mutation`。保存されている状態が変更を受けられないもの (別名の循環、使い切った更新の番号) は `stored-state-invalid`。そう名乗っていない reject は、storage から来たものとして扱い、`storage-update-failed` / `settings-update-failed` を返す (例外の型では分けられない。`TypeError` は、入力の検査でも、保存されている状態の異常でも投げられる)。知らない `type` のメッセージには答えず、[`createWriteListener`](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#writes) がログに出す。`background.js` が `importScripts` で取り込むスクリプト (core/common.js、channel-store.js、settings-store.js) は 1 つのグローバルを共有するので、トップレベルの名前が重なってはいけない (`node test.js` が、それらのファイルの宣言を突き合わせる)
- **Chrome の同期がオンなら設定は利用者の Chrome の間で同期され、チャンネルのデータは同期されない**: `autoLoudnessSettings` はチャンネルを 1 つも名指ししないので、`chrome.storage.sync` に置く。利用者が Chrome の同期をオンにしていれば、Chrome はそれを、利用者がサインインしているすべての Chrome と同期する。オフなら、sync の領域は local と同じに振る舞う。チャンネルごとに持つもの (`channelVolumes`、`channelVolumeAliases`、`channelVolumeSequence`) は、すべて `chrome.storage.local` に残す。見たチャンネルの数だけ増えていくのに、sync は全体で 100 KB、1 項目で 8 KB しか持てない
  - **読み取り**: [`readSettings`](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#settings) は、local にある写しを代わりに読む。以前の版が書いたプロファイルで、worker がまだ設定を移していないときのもの。content.js、popup.js、options.js、設定の書き手の「読む・変える・書く」は、すべてこれを通して読む。そのため、移し替えの前に行った書き込みは、空のオブジェクトから始めずに、local の値を sync へ持って行く。content.js は、同期された設定の変化のたびに進む `settingsRevision` を持つ。popup.js は、表示の単位を `followDisplayUnit` (core/common.js) で読み、これも同じように数える。どちらも、読み取りを出してから変化が来ていないときにだけ、読み取りが返した値を反映する。そのため、その間に届いた変化が、古い読み取りで取り消されることはない (options.js は、自分の番号ですでに同じことをしている)
  - **移し替え**: background.js は、トップレベルで `writeSettings.moveToSync()` を頼む。そのため、移し替えは worker の起動のたびに走り (失敗した移し替えは、次の起動でもう一度行う)、設定の書き手の列の中で走る (設定の書き込みと移し替えが入り混じることはない)。移し替えそのものは [`moveSettingsToSync`](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#settings)
  - **インストールのときは何も書かない**: どちらの領域にも設定が見つからなかった読み手は、既定値 (`DEFAULT_TARGET_LUFS`、`DEFAULT_AD_GAIN_DB`、`%`、オーバーレイはオン、Auto の既定値は両方オフ) を使う。だから、インストールのときにそれを書くことはない。Chrome の同期がオンのとき、利用者が新しくサインインした Chrome は、Chrome の同期がアカウントの持っているものを届けるまで、sync が空のままで始まる。その間に既定値を書くと、利用者がサインインしているすべての Chrome の sync が、その既定値になってしまう。設定を最初に書くのは、options での操作か、移し替え
  - **リスナー**: Chrome は、領域ごとに 1 つの onChanged イベントを出す。`autoLoudnessSettings` は `sync` の領域からだけ受け取る。local でこのキーが変わるのは、移し替えがそれを消すときだけで、その変化は `newValue` を持たない。それを設定として読むと、すべての設定が既定値に戻ってしまう。チャンネルのキーは `local` の領域からだけ受け取る。content.js、popup.js、options.js は、すべてこれを守る
  - **書き込みの上限**: sync が受け付ける書き込みは、1 分に約 120 回、1 時間に 1800 回。設定を書くのは、options でのはっきりした 1 回の操作 (range の `change`、range の値を動かすキーのうち最後まで押していたキーを離したとき、切り替えの `change`、単位のボタンの `click`。range の `input` はラベルを描き直すだけで、押したままのキーの繰り返しは何も書かない) と、移し替えだけ。計測や popup がすることは、設定を書かない
- **項目ごとの設定の保存**: options は、最初の読み込みが終わってから操作部を有効にし、変わった設定の項目だけを background.js → settings-store.js の列へ送る。複数の設定タブが、古い表示のまま別々の項目を変えたとき、`autoLoudnessSettings` は丸ごと置き換えられずに、最新の値へまとめられる
- **保存した値を入れてから画面を出す**: popup / options は、`body.initializing` で読み込み中の画面を隠し、i18n を入れて、保存した設定を描き終えてから外す (options は、読み込みが失敗したときも外す。出てこない画面は、操作することもできない)。初期化の間は、`body.initializing *` (と `::before` / `::after`) の `transition: none !important` が、すべての transition を止める。セレクターを並べて書く方法では、だれかが書き忘れた操作部が漏れる。`!important` が無いと、個別のセレクターが詳細度で勝つ。transition は値を書いた瞬間に動き出すので、これが無いと残りが画面の上で動き、「先に出して、あとで更新した」ように見える。読み込みが失敗した画面は、読めなかったもの (保存した設定) を名指しする。チャンネルの一覧については、その一覧を読めたときにだけ答える。読めたと数えるのは 2 つで、最初の読み取りと、変化の通知 (一覧そのものを運んでくる)。どちらかが届くまでは、「保存済みチャンネルなし」も、チャンネルの表も、マークアップにあるままの形では出さない。失敗が確定した後に届いた変化の通知は受け取らない (読み直しを頼んでいる画面に、別のタブの書き込みを出すことになるため)。それより前に届いた通知は、すでに画面に出ているので、そのまま残す。壊す操作 (全消去、行の ×) は、読み込みが成功したときだけ有効になる。ハンドラーも、終わっていない読み込みから来た変更を断る。読み込みは [`runPageLoad`](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#pages) を通して走る。その締め切りは、失敗と同じ形で読み込みを終わらせる (いつまでも決着しない読み込みが、画面を隠したままにしないようにするため)。締め切りの後に届いた読み取りは、画面に出さない。読み込みが書き込むまで画面にあるのは、マークアップの値。そのため、マークアップの初期値は、`renderSettings` が代わりに使う既定値と同じに保つ (`node test.js` が 2 つを突き合わせる)
- **CM 区間の検出**: 独立した 2 つの合図を使う
  - プレイヤーの cue: メディアのエンジンは worker の中で動き、CM を 1 つ流すたびに、ページへ cue を送る。`Worker` のコンストラクターを包んでメッセージのリスナーを足し、`rollType` と `startTime` / `endTime` を持つ cue を読む。この 2 つは、つないだ要素のメディアの時刻で表してあり、CM の終わりと一致する。CM の間は 2 つ目のプレイヤーが動き、別の時間軸で自分の CM の cue を出すので、区間に再生位置が入っている cue だけを受け取る。**受け取る区間と、CM かどうかの判定は別**。受け取りは始まりの 1 秒前から、CM の中だという判定は始まりから。こうして、早く届いた cue が本編に CM ゲインをかけないようにする。区間は CM を過ぎたら捨てるので、再生位置が戻っても同じ CM がもう一度開くことはない
  - cue をいつまで持つか: cue は、1 つのメディアと 1 つの要素のもの。計測のリセット (popup の操作や、持ち主の ID が確定したときにも走る) では捨てない。捨てるのは、次の 2 つの出来事のとき。**どちらの出来事でも、その出来事で無効になるものを全部捨てる**。片方だけを消すと、cue も DOM の CM 表示も効かない状態か、前のメディアの CM 表示が新しいメディアの CM として残る状態ができる
    - 要素の入れ替え: cue の時刻と、このメディアが cue を受け取ったことがあるか (`adCueSeen`)
    - `mediaChanged` (SPA 遷移): 上のものと、DOM の CM 表示の状態。content.js は、bridge とそろえるために `requestedAdActive` も消す。さらに、**遷移の瞬間にあった CM 表示の要素を控えておき、その要素そのものは新しいメディアの CM 表示として扱わない**。遷移の瞬間には古いプレイヤーがまだページにあり、その間に別の DOM の変化があると、observer が古い CM 表示を新しいメディアの CM として知らせてしまう。真偽の値ではなく要素として持つのは、MutationObserver が、古い要素の削除と新しい要素の追加を 1 回の呼び出しにまとめることがあり、そのときは CM 表示が消えた瞬間を見られないため。控えは、その要素が DOM から外れたら捨てる (同じ要素が戻されたら、新しいメディアのものとして受け取る)
      控えるのは、**最後に DOM を読んだときにあった要素**で、遷移の瞬間にページを読み直すことはしない。読み直す作りでは、「いつ読むか」がページ自身の順番と競り合う (プレイヤーが同じタスクの中で入れ替わる、ページ自身の popstate のリスナーが先に走る、同じ URL への History の呼び出しが混ざる)。そのため、読む瞬間そのものを持たない設計にしている。DOM は、遷移を処理する前に必ず読んであるので、そこにあった CM 表示は古いメディアのもの。これを成り立たせているのは、次の 3 つ:
      - `pushState` / `replaceState` のフックは、URL が動く前に DOM を読み直す (まだ見ていなかった CM 表示は、古いメディアのものとして控える)
      - 遷移を見張る MutationObserver は、CM 表示の observer より先に登録する (遷移を運んできたまとまりは、新しいメディアに対して読む)
      - 遷移の処理の最後に、DOM を読み直す (同じまとまりで届いた CM 表示は、次の DOM の変化を待たずに知らせる)
  - CM 枠の中のすき間: 1 つの CM 区間に広告がいくつも入っているとき、1 つの広告の終わりから次の cue までの間にも、再生位置は進む。区間を終わりで閉じるのは、cue が CM 枠の最後の広告だと言っているとき (`podPosition` >= `podCount` - 1) だけ。そうでないとき (途中の位置を指している、または値が読めない) は、次の cue を 0.4 秒待つ。届かなければ、そこで区間を閉じる
  - DOM: `[data-a-target="video-ad-countdown"]` / `[data-test-selector="ad-banner-default-text"]` があるかどうか
- **2 つの合図の使い分け**: cue は、CM の最初の音とほぼ同時に届き、CM の終わりを正確に示す。DOM の CM 表示は、CM の最初の音より遅れて現れ、CM の後も DOM に残ることがある。そこで、cue を 1 つでも受け取ったメディアは、cue だけで開き、閉じる。cue を受け取らないメディア (VOD のクライアント側の CM) は、代わりに DOM の CM 表示を使う
- **CM 要素**: VOD の CM は、本編の要素が止まったまま、別の `<video>` で流れる。その要素は本編の要素の音量に従わず、自分の音量で鳴る。本編の要素が止まっていて、別の要素が鳴っていて、そのメディアが Web Audio で運べるものなら、その要素にも `MediaElementSource` + `GainNode` を入れ、`baseline * adGainOffset * (本編の音量 / その要素の音量)` をかける。別のオリジンが配るメディアを持つ CM 要素は、ほかの要素と同じように触らず、何も知らせない。そのため CM ゲインは届かず、その要素は自分の音量で鳴り続ける。CM が終わるとゲインは 1.0 に戻り、要素が DOM から外れたら、つなぎを外す。この要素からは計測しない
- **CM の間の動き**: GainNode に baseline × adGainOffset (dB → ゲイン) をかける。CM の間は Integrated の計測を飛ばし、本編の値を保つ。CM が終わる瞬間のブロックには CM の音が入っていることがあるので、CM の後も、ゲーティング窓が CM を抜けるまでの 4 窓を Integrated から外す。CM の始まりの側では、DOM の目印が CM の最初の音より遅れて現れるので、検出したときに直近の 5 窓 (0.5 秒) を取り消す。取り消す範囲に、境界のスキップがすでに外した窓が入っていれば、その数を取り消す数から引く。足していない窓は取り消せず、頼まれた数をそのまま通すと、代わりに本編の窓を消してしまう。取り消す窓の数は、観測した目印の遅れに合わせてある。本編の窓まで消すと、そのレベルがゲートの母集団から抜け、Integrated の値が動く
- **プレイヤーの音量を打ち消す**: 計測の取り出し口は `sourceNode` のすぐ後にあり、Twitch のプレイヤーの音量 (`video.volume`) は、それより上流で効く。各ブロックの MS を volume² で割り、Integrated LUFS を音量 1.0 のときの値に保つ。スライダーを下げても、計算したゲインは上がらない。音量の変化をまたぐゲーティング窓は、CM の境界と同じ仕組みで外す
- **保存した値が持つ参照**: 参照の名前を持つのは、音量 1.0 に対して取った値だけ。保存した LUFS は `lastLufsRef` と、保存した Auto のゲインは `autoGainRef` と一緒に、それぞれ自分の項目の更新の番号でまとめる (番号を 1 つにまとめると、ID をまとめるときに、値と参照の組が入れ替わる)。窓の数 `lastLufsWindows` は、`lastLufsRef` と同じく LUFS の側のもので、値が勝った側のものを残す。参照の無い値 (拡張機能の更新より前に保存したもの) は、計測の最初のサンプルに使わない。参照の無い Auto のゲインは、起動のときにかけない。手動ゲインは視聴者自身の設定なので、これまでどおりかける
- **値がまだ無い間の Suggested gain**: ゲートを通った値がまだ無い間、`suggestedGain` は 1.0 を返し、ゲインを上げる提案をしない
- **createMediaElementSource**: 1 つの `<video>` につき 1 回しか呼べない。別の拡張機能が先に取っていると失敗する。失敗した video は `WeakSet` で外し、別の video へつなぎに行く。つなげなかった video では、GainNode もプレイヤーの音声の経路の外にある。そのため content.js は `attach-failed` を受け取り、理由と直し方を popup に出し、今かかっているゲインの表示 (オーバーレイ) を取り下げる。別の video へのつなぎが成功しても、取られた要素がページに残っている間は、音はその要素を通って鳴り続ける。そのため、`attached` の `takenElsewhere` で知らせを出したままにする
- **別のオリジンが配るメディア**: `MediaElementAudioSourceNode` は、要素が別のオリジンのリソースを CORS モードの外で読み込んだとき、無音を出す。そして、node ができた後は、要素の音はプレイヤーへ戻らない。だから、そういう要素は取らずに、そのままにする。Twitch のクリップは、この形で配られる。クリップの要素は CDN の MP4 を再生し、`crossorigin` 属性を持たない。Live と VOD は、ページ自身のオリジンの `MediaSource` を通って届く。要素に届くと数えるのは、`srcObject` があるとき、リソースがページのオリジンから来ているとき、`crossorigin` 属性を持つとき。まだ何も読み込んでいない要素は、どちらとも決まらないので、つなぐためのループが 1 秒後にもう一度確かめる。届かない要素は、ページにほかに取れる要素がある間は飛ばし、最後の 1 つになったときだけ `attach` に渡す。そのため、両方を持つページはゲインを保ち、その要素しか無いページでも、断ったことが知らされる。断ったことは、原因 `cross-origin` の `attach-failed` として content.js に届く。content.js は、その要素のゲインと計測を止め、popup にそう出す。この知らせは、プレイヤーの経路だけが、要素ごとに 1 回出す。CM の経路は自分用の記録を別に持つので、その 1 回を使ってしまうことはない。content.js は、この原因を info で、ほかの原因を warn でログに出す (Chrome は content script の warn を拡張機能のエラーとして集める。そして、視聴者にできることが何も無い原因は、これだけ)。代わりにクリップを CORS モードで取りに行く手は使えない。`crossorigin` を付けると、プレイヤーが出す range の要求に `Access-Control-Allow-Origin` ヘッダーの無い応答が返り、クリップがまったく読み込まれない
- **クリップは音量を調整しない**: Twitch のクリップはすべて上の形で配られるので、拡張機能にはクリップの音に届く手段が無い。クリップは、動くときもある場面ではなく、対象外にする。クリップは、チャンネルも、保存したゲインも、Auto の設定も持たず、持ち主の問い合わせもしない。popup は、何もできない操作部の画面の代わりに、状態の行だけを出す。以前の版がクリップのために保存したものは、store が次に書くときに消す。行の中身がクリップだけだったなら、行と仮の名前まで消す
- **操作は 1 つの状態に対して行い、その状態にだけ効く**: content.js が返す答えは、どれも `appliesTo` を持つ。URL が指すチャンネル、メディアの種別、動画のことで、数えた値ではなく状態から導くので、進めなければならない目印が無い。popup は、スライダー、Suggested gain のボタン、Auto の切り替え、計測のリセットと一緒に、それを送り返す。状態が先へ進んでしまった操作は、入れ替わった後の状態にかけずに、`state moved` で断る。これが無いと、`setGain` は、操作が届いたときにタブが持っていたチャンネルを使っていた。ルートが変わる途中で離したスライダーが、1 つのチャンネルのゲインを別のチャンネルの項目に、そのチャンネルを見ていた種別で書き込んだ (測って確かめた)。動画が状態に入っているのは、bridge が持ち主を知らせた後は、同じ持ち主の 2 つの VOD がチャンネル id と種別を共有し、popup が出している計測値は再生していた方のものだから
- **AudioContext が止まっているとき**: Chrome は、ページが操作されるまで、context を止まった状態 (suspended) で始める。media element source は、その context をプレイヤーとスピーカーの間に入れるので、止まっている間はプレイヤーが無音になる。bridge は、作ったとき、変化のたび、`resume` への答えとして、状態を知らせる。content.js は、知らされた状態が `running` になるまで、document の `click` と `keydown` のたびに capture フェーズで `resume` を頼み、動かなくなったら、また受け始める。回復を 1 回の操作に任せることはできない。操作は context ができる前に来ることがある (だから `resume` は context を作る)。プレイヤーのキーボードのショートカットでミュートを解いた視聴者は、click を 1 回も送らない。Chrome は、ページがどこかで操作されたことがあれば resume を受け付けるので、resume を操作と同じタスクの中で走らせる必要は無い
- **AudioContext を作れないとき**: 失敗した試みは覚えておかず、次の attach でもう一度作る。失敗の知らせは、状態が変わったときに 1 回だけ送る (やり直しのたびには送らない)。`cause: 'audio-context'` で、別の拡張機能とのぶつかりと区別し、popup は読み直しを頼む別の文を出す
- **音声の経路が無い間の値**: `attach-failed` の後や `takenElsewhere` の間に届いた lufs は、視聴者が聞いている要素のものではないので、捨てる (保存せず、Auto も追従しない)。回復した瞬間に、計測をリセットする。bridge のリングバッファには、別の要素のブロックがまだ残っている
- **計測の経路だけが使えないとき**: worklet の読み込みやつなぎが失敗しても、GainNode は経路の中にある。そこで、`attached` の `measuring: false` で「計測だけが使えない」と知らせ、音量の調整はまだ効くと伝える別の文を出す。CM の状態と CM 要素のゲインを読み直すのは、計測のブロック。そのため、計測のつなぎが無いつなぎ方では、代わりにブロックと同じ間隔 (100 ms) のタイマーで読み直す。再生位置は、これまでどおり cue のある区間を開いて閉じ、CM 要素は、プレイヤーの音量、自分の音量、別の要素で始まる広告に、これまでどおり従う。タイマーは、つなぎと一緒に無くなる
- **つなぎ直しの繰り返し**: document_start の時点では video 要素が無いので、`scheduleAttach()` が 1 秒おきに回る。`clearStaleAttachment()` は、DOM から外れた video を見つけ、つなぎ直せるようにする (Twitch の SPA が video を入れ替える場合のため)。content.js も、SPA 遷移のときに `attach` をもう一度送る
- **計測のつなぎをつなぐ場所**: `attach()` は `ensureContext()` を await し、その await は `audioWorklet.addModule()` の決着まで含む。そのため、worklet が使えるかどうかは、attach の時点で決まっている。読み込みが失敗した attach は `measuring: false` を知らせ、そのつなぎには、後から計測の経路を足さない
- **SPA 遷移**: 3 つの層がある。history.pushState/replaceState のフック + popstate + MutationObserver。URL が変わると、resetMeasurement + 種別の分類のやり直し + もう一度の `attach` が走る
- **計測のリセットの epoch の番号**: content.js は、resetMeasurement を送るたびに epoch の番号を進め、page-bridge は、その後の lufs の通知にその番号を付ける。content.js は、今の epoch より古い通知を捨てる。そのため、リセットを送る前に page-bridge が計算したブロックが、保存した LUFS を生き返らせることはない
- **Live/VOD ごとに別のゲイン**: 配信の音は時間帯で変わるので、種別ごとに別々に持つ。同じチャンネルの過去の VOD のゲインを、今の Live に写すことはしない
- **Twitch の予約済みのパス**: `/directory`、`/settings`、`/videos`、`/p`、`/jobs` などは、Live のチャンネルと読み違えないように、TWITCH_RESERVED_PATHS で除く
- **予約済みの名前**: Chrome が「パッケージ化されていない拡張機能を読み込む」(Load unpacked) で断るのは、ルート直下にある `_` で始まる名前。サブディレクトリの `_metadata` などは読み込める (`_locales` はルート直下でも許される)。`test.js` の走査はそれより厳しい。パッケージのもとになるツリー (リポジトリから `.git` / `node_modules` と、ルート直下の `work/` / `.claude/` を除いたもの) の中で、どの深さにあっても、そういう名前を報告する。`docs/` など、zip に入らないディレクトリも対象になる
- **パッケージは参照のつながりで選ぶ**: `pack.py` が選ぶのは、manifest からたどれるもの (content_scripts / web_accessible_resources / service_worker / options_page と options_ui.page / action.default_popup / devtools_page / side_panel.default_path / chrome_url_overrides / sandbox.pages / storage.managed_schema / declarative_net_request.rule_resources / icons と action.default_icon の js と css。最後のものは、1 つのパスで書いても、サイズごとに書いてもよい)、それらの HTML ファイルの `<script src>` と `<link href>` の css、スタイルシート自身の `@import` と `url()`、worker の `importScripts`、`_locales/<locale>/messages.json`、そして `LICENSE`。`LICENSE` は、パッケージの中のどれも読み込まないが、いつも入れる (MIT の表示はどの写しにも付いて回る。無ければ pack.py は失敗する)。それ以外は入れない。どこからも参照されていないファイルは、拡張子が何であっても入らない。パスは 1 つの解決の処理を通る。絶対パス、`..`、先がパッケージの外に出るシンボリックリンク (途中のディレクトリにあるものも含む) は、失敗にする (壊れた zip も、外のファイルを入れた zip も、黙って作ることはない)
- **CSP**: AudioWorklet のモジュールは、web_accessible_resources で公開する。page-bridge は、MAIN world でページ自身のスクリプトと window を共有していて、ページは init を含むどのコマンドでも送れる。そのため、page-bridge はモジュールの URL を受け取らない。自分のスタックのフレームから拡張機能のオリジンを読み、`<origin>/audio-worklet.js` を読み込む。オリジンが分からないときは、モジュールを読み込まない
- **NaN/Infinity への備え**: 値が無限大や NaN のときは、ゲイン 1.0 にする
